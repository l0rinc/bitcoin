Exploitability: kernel-API consumer with snapshot-chainstate datadir + `set_wipe_dbs(1,1)` -> deterministic crash in `btck_chainstate_manager_create`; bitcoind unaffected. Priority: LOW-MEDIUM (kernel-API crash, needs crafted datadir + explicit wipe).
2. `b8fcf9ed17` wallet: fail encryption when the master key record write fails. `CWallet::EncryptWallet()` discarded the `WriteMasterKey()` result — the only unchecked step in the failure sequence. SQLite record statements are independent, so a failed record write does not poison COMMIT: encrypted keys persist with no `mkey` record = permanent lockout, reported as success. Reproduced via `wallet_tests/encrypt_wallet_master_key_write_failure` with an in-memory DB whose `SQLiteBatch::WriteKey` override fails exactly the `mkey` record (failure injection, temp-armed). Failing before: returns `true` + `walletdescriptorckey` committed, no `mkey`. Passing after: returns `false`, nothing persisted. Master has the same discarded result (wallet.cpp:864). Exploitability: needs a transient SQLite I/O error on exactly the mkey record during encryption (disk full / I/O hiccup); not remotely triggerable, but funds-at-risk correctness. Priority: MEDIUM.
3. `501bd2e263` wallet: fail passphrase change when the master key record write fails. Same defect class, different site ("fixed in one place, present in another"). `CWallet::ChangeWalletPassphrase()` discarded the same result with no transaction wrapper: failed write leaves the in-memory master key re-encrypted with the new passphrase while disk keeps the old — silent divergence, new passphrase works in-memory, old after reload. Reproduced via `wallet_tests/change_passphrase_master_key_write_failure` (encrypt, then arm the injection, then change passphrase). Failing before: returns `true` + `Unlock("old_pass")` fails. Passing after: returns `false`, in-memory record restored, `Unlock("old_pass")` works. Master has it too (wallet.cpp:657). Priority: LOW-MEDIUM.
4. `3be812ef57` wallet: fail encryption when a crypted key record write fails. Third site of the same class, found by grepping every discarded `WalletBatch` Write/Erase result in src/wallet after sites 2-3. `DescriptorScriptPubKeyMan::Encrypt()` discarded `WriteCryptedDescriptorKey()`; since that function erases the plaintext record only after a successful crypted write (walletdb.cpp:230), a failed write leaves plaintext on disk while COMMIT persists the other keys' crypted records → next load sees BOTH record types → `DescriptorScriptPubKeyMan` ctor throws "Wallet contains both unencrypted and encrypted keys" → wallet refuses to load, reported as successful encryption. Failing before: `Encrypt()` returns `true`; temp-mutated commit variant (not committed) proved exactly 1 plaintext + 1 crypted record persisted = the throw state. Passing after: returns `false`, TxnAbort, 2 plaintext/0 crypted remain; 17-case wallet_tests green ASan + Release. Master has it (scriptpubkeyman.cpp:968); stack never touched the file (empty diff vs master). Priority: MEDIUM (same funds-at-risk class as #2).

- CI mutable image tags (ubuntu:26.04, debian:trixie): deliberate CI freshness. ci.yml missing top-level `permissions:`: unverifiable from tree (token scope = repo default).
- All other `m_mempool->` derefs in validation.cpp (2026-07-19 sweep): every one guarded (`if (m_mempool)`, early return in `MaybeUpdateMempoolForReorg`, `disconnectpool && m_mempool`); only DeleteChainstate was unguarded. Kernel null-mempool surface otherwise clean.
- `DescriptorScriptPubKeyMan::TopUp` discarded `WriteDescriptor` (scriptpubkeyman.cpp:1106): self-healing — descriptors re-derive deterministically on load, so a lost range record is rewritten by the next top-up; no loss.
- Legacy checksum rewrite `batch.WriteCryptedKey` discard (scriptpubkeyman.cpp:240, unlock-time best-effort re-write with checksums): old record stays valid on failure, retried next unlock; benign (legacy-data path).
- Bookkeeping discards (`WriteBestBlock`, `WriteOrderPosNext`, `WriteTx`, receive requests; wallet.cpp/export.cpp): worst case is a rescan or re-announced state, no key material involved.
- IPC unset-field server crash (claimed by an abandoned uncommitted working-tree change found 2026-07-19, never committed, now reverted): the change removed `assert(input.has())` from the `Deserializable` `CustomReadField` overload (src/ipc/capnp/common-types.h) claiming a client omitting a Data field aborts the server, plus a fuzz arm expecting rejection. FALSIFIED empirically on both counts: with the assert present (master state), a `passTransaction` request with unset `tx` Data is silently accepted (null `CTransactionRef`, the deliberate empty↔null design of upstream `f16b3613cd`/`CustomHasField(TypeList<CTransaction>)`), and a `passOutPoint` request with unset `arg` is likewise accepted with a default `COutPoint` (mp framework: all capnp fields optional, un-constructible params default). The assert is dead code for unset request fields; the fuzz arm's reject expectation contradicts upstream design. Proof: seed `\x06\x01` (LIMITED_WHILE bool + CallOneOf arm 6) run against `FUZZ=ipc` with assert restored — both probes returned "unexpectedly accepted" (RawIpcError), no abort. Silent defaulting of omitted args is the documented mp framework contract (proxy-types.h design note), not a server bug.
